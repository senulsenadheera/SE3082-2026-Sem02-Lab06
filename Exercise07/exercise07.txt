Answer
---------------------------------------------------------------------------------
Parallelizing this code required three changes beyond simply adding a parallel region, each addressing a variable that would otherwise be shared incorrectly. First, the complex number c was a file-scope global written by the loop body and read by testpoint, so with multiple threads every thread would overwrite the same memory and points would be tested against whichever value happened to be written last, producing a wrong and non-deterministic area; the fix was to remove the global, declare c inside the parallel region so each thread has its own copy, and pass it into testpoint as an argument. Second, numoutside is incremented by every thread and is a read-modify-write operation, so it is a classic data race of the kind seen in Lab 04, and it was handled with reduction(+:numoutside), which gives each thread a private partial count and combines them once at the end rather than synchronising on all four million updates. Third, the loop counters i and j were declared private so that threads do not interfere with each other's position in the iteration space. For the work distribution the exercise asks for OpenMP library routines rather than a parallel for, so each thread calls omp_get_thread_num and omp_get_num_threads and takes every nth row of the outer loop starting from its own thread id, which is a cyclic distribution giving each thread an equal number of rows. Cyclic was chosen over contiguous blocks deliberately, because the cost of a point is not uniform: points outside the Set exit early on the |z| > 2 test while points inside run the full 2000 iterations, so a block distribution would hand one thread the dense interior of the Set and leave the others idle, whereas interleaving the rows spreads both cheap and expensive rows evenly across the team.

The results confirm the parallelisation is correct and effective. The area comes out as 1.50926484 with 1, 2, 3 and 4 threads, identical to the serial result and identical to eight decimal places across all thread counts, which confirms the shared variable problems were properly resolved, since any remaining race on c or numoutside would show up immediately as a varying answer. Taking the single-threaded parallel run of 9.986 seconds as the baseline, the time falls to 5.182 seconds at two threads, a speedup of 1.93 and a parallel efficiency of 96 percent, which is close to the theoretical maximum and indicates the cyclic distribution has balanced the load almost perfectly. Adding a third and fourth thread gives no further improvement, with times of 5.103 and 5.170 seconds, because the EC2 instance has only two vCPUs and additional threads simply time-share the same two cores while adding scheduling overhead. The single-threaded parallel run is essentially the same speed as the serial version at 9.986 against 10.243 seconds, showing that the cost of creating the parallel region and performing the reduction is negligible relative to the ten seconds of computation. This kernel scales far better than the array multiplication in Exercise 6, which reached only 1.24 at two threads, and the reason is arithmetic intensity: each grid point performs up to 2000 floating point iterations on values held entirely in registers, so the problem is compute bound and the memory bus is never the limiting factor, whereas the element-wise multiplication performed a single multiply per 24 bytes of memory traffic and saturated bandwidth with a single thread.
